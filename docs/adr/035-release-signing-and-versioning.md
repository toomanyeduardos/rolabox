# ADR-035: Releases are signed with an upload key kept outside the repo, Google holds the app signing key, and the version comes from one semver property

- **Status:** Accepted
- **Date:** 2026-11-19
- **Author:** Eduardo Flores
- **Reviewers:** AI-assisted review
- **Revised 2026-11-20:** Rules 1, 2 and 4 are built in launch/01, so they are `[enforced]`, no longer
  `[planned]`, and Conformance describes the checks as they are. The decision is unchanged.

## Context

Rolabox is going onto Google Play (launch/00). Two things in the build stop that today:

- **Release builds are signed with the debug key.** `configureReleaseOptimization()` in
  `build-logic/.../ReleaseOptimization.kt` sets `signingConfig = signingConfigs.getByName("debug")`
  so a minified build can be installed and smoke-tested. Play rejects a debug-signed upload.
- **The version is two literals.** `app/build.gradle.kts` sets `versionCode = 1` and
  `versionName = "1.0"`. Play rejects an upload whose `versionCode` isn't higher than every one it
  already has, on any track.

What Play asks for:

- **An app bundle (AAB),** not an APK. The R8 mapping file travels inside it, so Play Console
  deobfuscates crashes ([ADR-030](030-crash-reporting.md)).
- **Play App Signing,** which is required for new apps. Google holds the **app signing key**, and
  signs the APKs it delivers with it. The developer keeps an **upload key**, signs each bundle with
  it, and Play checks that signature on upload. A lost or leaked upload key can be reset through
  Play Console support. A lost app signing key can't be replaced, which is why Google holds it.

What the build has to keep doing:

- **A fresh clone builds everything,** with no secrets ([ADR-008](008-one-app-with-an-optional-account.md),
  "One CI build"). CI runs `./gradlew :app:checkReleaseApkAudio`, which builds the release APK, on
  every PR, including PRs from forks, which get no secrets.
- **A minified build can be installed locally** for the manual smoke test before each release
  (`ReleaseOptimization.kt`; launch/15). An unsigned APK can't be installed.

Rolabox is open source, so anything in the repo is public, and there is one maintainer, who builds
and uploads releases by hand for v1. CI signing and uploading are launch/16, after v1.

The app uses Sign in with Google ([ADR-013](013-account-linking.md)). Google's sign-in checks the
SHA-1 of the key that signed the installed APK against the Firebase project, so whichever keys sign
an APK that a user signs in from have to be registered there.

## Decision

We will sign releases with an **upload key** that lives only on the maintainer's machine and in
their backups, enrol the app in **Play App Signing** with a key that Google generates and holds,
read the signing values from **Gradle properties outside the repo**, keep signing with the **debug
key when none are set**, and derive `versionCode` from a **semver `versionName` in the repo's
`gradle.properties`**.

### The keys

| Key | Who holds it | Signs | Lost |
| --- | --- | --- | --- |
| App signing key | Google, generated in Play Console when the app is enrolled | Every APK Play delivers | Can't happen: Google keeps it |
| Upload key | The maintainer | Every bundle uploaded to Play | Reset through Play Console, then the new key's certificate is uploaded |
| Debug key | Every developer's `~/.android/debug.keystore` | Debug builds, and release builds with no signing values | Regenerated by the Android tools |

- **The upload key** is an RSA key of 4096 bits in a PKCS12 keystore, valid for 30 years, made with
  `keytool`. It is used for nothing but Rolabox's uploads.
- **It is backed up** in the maintainer's password manager (the keystore file, both passwords and
  the alias, in one entry) and on one offline copy. Where each copy is, and how to reset the key, is
  written in the release steps (below), not in this ADR.
- **The app is enrolled with a key Google generates,** not one we upload. Nothing outside Google
  ever holds the app signing key.
- **Firebase knows the keys that sign what users install.** The app signing key's SHA-1 and SHA-256,
  shown in Play Console, are added to the Firebase project of the Play build, and so is the upload
  key's, so a locally built signed release can sign in during the smoke test. Which Firebase project
  that is, is launch/02.

### Where the signing values come from

The release signing config is read from four Gradle properties:

| Property | Value |
| --- | --- |
| `rolaboxUploadStoreFile` | Absolute path to the upload keystore |
| `rolaboxUploadStorePassword` | The keystore's password |
| `rolaboxUploadKeyAlias` | The key's alias |
| `rolaboxUploadKeyPassword` | The key's password |

- **They are set outside the repo:** in `~/.gradle/gradle.properties` on the maintainer's machine,
  or as `ORG_GRADLE_PROJECT_<name>` environment variables, which is how CI will pass them as secrets
  in launch/16. Never in the repo's `gradle.properties`, in `local.properties`, or in a build file.
- **They are read lazily** through `providers.gradleProperty`, so the configuration cache keeps
  working and a value never ends up in a committed file.
- **The keystore is never in the repo.** `.gitignore` covers `*.jks`, `*.keystore` and `*.p12` at
  any path, and CI fails if a tracked file has one of those extensions, as it does for
  `google-services.json` (ADR-008, rule 5).

### With and without the values

| Signing properties set | Release is signed with | For |
| --- | --- | --- |
| All four | The upload key | Bundles uploaded to Play |
| None | The debug key | Fresh clones, CI, and the local smoke test |
| Some, not all | Nothing: the build fails, naming the missing ones | Catching a typo before it becomes a debug-signed bundle |

The debug fallback stays because it is the only option that keeps both a fresh clone's release
build and the smoke test working without secrets, and it can't ship: Play rejects a debug-signed
bundle on upload. When it applies, the build logs a warning on `bundleRelease` and
`assembleRelease` that says the output can't be uploaded to Play.

### Where it lives

Signing is configured in the application convention plugin, `rolabox.android.application`, in a
`ReleaseSigning.kt` next to `ReleaseOptimization.kt`, and replaces the debug-signing line there.
[ADR-004](004-convention-plugins.md) rule 2 is about configuration shared by more than one module,
and only `:app` is an application. But the release build type is already configured there (R8,
ADR-030's Crashlytics), the checks that fail the build live there, and `:app`'s build file stays
within ADR-004 rule 3.

### The version

- **`versionName` is semver,** `MAJOR.MINOR.PATCH`, set once as `rolabox.versionName` in the repo's
  `gradle.properties`. v1 is `1.0.0`.
- **`versionCode` is derived from it:** `MAJOR * 10000 + MINOR * 100 + PATCH`, so `1.0.0` is
  `10000` and `1.2.3` is `10203`. `MINOR` and `PATCH` go from 0 to 99, and `MAJOR` from 1 to 209999,
  so the code stays under Play's limit of 2100000000 and always grows when the name does.
- **The convention plugin sets both** on `defaultConfig`, and fails the build if the property is
  missing or isn't in that form. `app/build.gradle.kts` sets neither.
- **Every upload to Play bumps the version,** even a rebuild for the same changes, since Play never
  accepts a `versionCode` twice. The commit that bumps it is tagged `v<versionName>`, which is what
  launch/16 will build from.
- Debug and release builds have the same version. There is no suffix and no build number.

### The release steps

The steps for a release (bump the version, tag, `./gradlew bundleRelease` with the signing values
set, upload the bundle) and the upload key's backup locations and reset procedure are written in
`docs/releasing.md`. The README links to it (launch/14).

## Alternatives considered

- **Sign with our own app signing key, without Play App Signing.** Not possible for a new app on
  Play, and it would put the one unrecoverable key on a laptop.
- **Upload our own app signing key to Play App Signing.** Lets the same key sign builds outside
  Play, but Rolabox ships only on Play, and it means a copy of the unrecoverable key existed outside
  Google at some point.
- **No release signing without the values: an unsigned release.** Can't ship by mistake either, but
  the smoke test then needs a signed build every time, which means the upload key on every machine
  that tests, and a fresh clone can't install its own release build.
- **Fail the release build without the values.** The strictest, but CI's `checkReleaseApkAudio` and
  every contributor's release build would need secrets, which ADR-008's one CI build forbids for
  PRs from forks.
- **Signing values in `local.properties`.** Also outside Git, but AGP owns that file, it's per
  checkout instead of per machine, and CI would need a second way to pass the values anyway.
  Gradle properties cover the machine and CI with one mechanism.
- **Signing in `:app`'s build file.** Fits ADR-004 rule 3's "settings unique to that module", but
  splits the release build type across two places and puts the checks that fail the build away from
  what they check.
- **`versionCode` from the Git commit count.** No number to keep, but CI's shallow clones count
  wrong, and a rewritten history can make the code go down.
- **`versionCode` from the CI run number.** Ties every release to CI, which v1 doesn't upload from,
  and gives no meaning to the number.
- **Two hand-kept numbers, `versionCode` and `versionName`.** The usual setup, but two numbers to
  bump in step, and nothing stops a name bump without a code bump until Play rejects the upload.

## Consequences

- A fresh clone and CI keep building, testing and checking the release APK with no secrets.
- Only the maintainer's machine can produce a bundle Play accepts, until launch/16 gives CI the
  secrets.
- A leaked upload key is an inconvenience, not a disaster: reset it, and nobody can publish an
  update with the old one. Losing it costs a support request and a few days.
- The version is one line to change, and a malformed one fails the build before it fails an upload.
- `MINOR` and `PATCH` can't pass 99. A 100th patch of a minor version means a new minor version.
- A debug-signed bundle can still be built and uploaded by mistake. Play rejects it, and the build's
  warning says so first.
- Sign in with Google on a release depends on the right SHA-1s being in Firebase, which is a manual
  step in Play Console and the Firebase console, outside anything the build can check.

## Rules

1. `[enforced]` The release build type's signing config is set only by
   `rolabox.android.application`. It uses the upload key when the four `rolaboxUpload*` properties
   are all set, the debug key when none are, and the build fails when only some are.
2. `[enforced]` No keystore is committed: `.gitignore` covers `*.jks`, `*.keystore` and
   `*.p12` at any path, and CI fails if a tracked file has one of those extensions.
3. `[convention]` The signing properties are set only in `~/.gradle/gradle.properties` or as
   environment variables: never in a file in the repo. No password, alias or keystore path is
   written in the repo.
4. `[enforced]` `versionName` comes from `rolabox.versionName` in `gradle.properties`, in
   the form `MAJOR.MINOR.PATCH`, and `versionCode` is `MAJOR * 10000 + MINOR * 100 + PATCH`. The
   convention plugin sets both, the build fails on a missing or malformed version, and no module
   sets either.
5. `[convention]` Every bundle uploaded to Play has a version no earlier upload had, and its commit
   is tagged `v<versionName>`.
6. `[convention]` What is uploaded to Play is the AAB from `bundleRelease`, never an APK.
7. `[convention]` The app is enrolled in Play App Signing with a key Google generates. The upload key
   is used only for Rolabox, and is backed up in the password manager and offline.
8. `[convention]` The SHA-1 and SHA-256 of the app signing key and of the upload key are in the
   Firebase project of the Play build.

**Conformance.** Rule 1 is checked by `ReleaseSigning.kt` when the build is configured, which also
fails when the release's final signing config isn't the one it chose, with a test of the all, none
and some cases in `build-logic`'s unit tests (`ReleaseSigningTest`). Rule 2 is a "No keystore committed" step in
[CI](../../.github/workflows/ci.yml). Rule 4 is checked by the convention plugin, which reads the
variant's final `versionCode` and `versionName`, so a module that sets either fails the build, with
a test of the derivation and of malformed versions. Rules 3 and 5 to 8 are reviewed, and rules 5 to
8 are steps in `docs/releasing.md`.
